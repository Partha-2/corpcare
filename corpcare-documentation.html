1 Project Overview
CorpCare — Corporate Health Management Platform

CorpCare is a B2B platform where companies onboard their employees, save their health vitals, and book health checkup appointments at partner hospitals. After booking, employees automatically receive a WhatsApp confirmation via Twilio and a voice confirmation call via Bolna AI.

FrontendReact + Vite → Vercel
Voice CallsBolna AI (Nova agent)
WhatsAppTwilio WhatsApp Sandbox
DeploymentRender (backend) + Vercel (frontend)

Booking details sent to employee's WhatsApp immediately after booking

5 Issues Faced & Troubleshooting
Issue 1 Bolna call cutting mid-conversation
Cause: Silence timeout too low + agent prompt had no instruction to wait for response.
Fix: Increased endpointing to 2000ms, added explicit wait instructions after each question in the prompt, removed name pronunciation from agent.
Issue 2 Employee name not recognized by Bolna STT
Cause: Agent repeated employee names back — STT would mishear Indian names.
Fix: Removed name repetition from prompt entirely, replaced with "Hi there" greeting, set speech speed to 0.85.
Issue 3 WhatsApp messages not delivered to new numbers
Cause: Twilio sandbox requires every new number to opt-in by sending a join message first.
Fix: Shared join code with testers for demo. Applied for Twilio WhatsApp Business API for production (Meta approval 1-7 days).
Issue 4 Bolna could not call new/unverified numbers
Cause: Bolna trial plan restricts outbound calls to verified numbers only.
Fix: Added numbers manually to Verified Numbers list in Bolna Settings. Production fix: purchase Bolna credits to unlock all numbers.
Issue 5 Slot double booking under concurrent requests
Cause: isBooked check and update were two separate operations — race condition.
Fix: Added @Transactional on bookAppointment() ensuring read-check-write is atomic. Database unique constraint on slot as final safety net.
6 Interview Questions & Answers

CorpCare is a B2B corporate health management platform. The problem it solves: companies struggle to coordinate annual health checkups for hundreds of employees across multiple hospitals. CorpCare centralises client onboarding, employee health records, hospital slot management, and automated appointment booking with voice and WhatsApp confirmation in one platform.

Each corporate client is a tenant. Employees strictly belong to one client via a foreign key relationship (client_id on the employees table). All API endpoints are scoped to clientId — one company cannot access another's data. A max employee limit of 100 is enforced at the service layer before persisting. The frontend also uses JWT-based role isolation: CLIENT users only see their own company's data.

Three-layer prevention:

  • Service layer: Checks isBooked flag before booking and throws 409 Conflict if already booked.
  • Transactional: @Transactional on bookAppointment() ensures check and update happen atomically within a single DB transaction.
  • Database: Unique constraint on the slot table as a final safety net.

After a successful booking is saved, AppointmentService calls NotificationService which makes a POST request to the Bolna API with the agent ID (87bf2a9f-3da8-47cb-b3cb-3f6cc112c4f1), employee phone number, and user_data containing hospital name, slot date, shift type, and purpose of visit. Bolna then places an automated voice call using the configured Nova agent — a 5-step conversation script that greets, confirms appointment details, asks purpose of visit, handles reschedules, and gracefully ends.

Hospitals operate in 3 fixed 8-hour shifts:

  • Morning — 8AM to 4PM
  • Evening — 4PM to 12AM
  • Night — 12AM to 8AM

Each shift on a given date is one AppointmentSlot. A slot has an isBooked boolean flag. Once an employee books a slot, isBooked is set to true and the slot no longer appears in available-slot queries. This ensures 1 slot = 1 person.

A @ControllerAdvice class intercepts all exceptions globally. Custom exceptions like SlotAlreadyBookedException, EmployeeNotFoundException, ClientCapacityExceededException are mapped to appropriate HTTP status codes (409, 404, 400). AccessDeniedException maps to 403. All responses follow a standard JSON wrapper: {status, message, data}.

Without @Transactional, two concurrent requests could both pass the isBooked check simultaneously before either updates the flag — causing a double booking. @Transactional ensures the read-check-write sequence is atomic within a single database transaction. The transaction isolation level ensures one request sees the other's update before proceeding.

  • JWT authentication per client tenant (data isolation already done)
  • Twilio WhatsApp Business API — remove sandbox opt-in requirement
  • Bolna paid plan — unrestricted outbound calls to any number
  • Slot auto-generation — hospitals define a date range and all slots are created automatically
  • Admin dashboard — HR-wide view of all employee appointments across clients
  • Retry mechanism — failed Bolna calls retried with exponential backoff
  • Async notification — use @Async so API response is not blocked by Bolna/Twilio latency

React frontend deployed on Vercel makes REST API calls to the Spring Boot backend deployed on Render. Axios is used as the HTTP client with a base URL configured via VITE_API_URL environment variable. CORS is configured on the Spring Boot side to allow requests from the Vercel domain. The Axios interceptor automatically attaches the JWT Bearer token to every request and redirects to login on 401/403 responses.

It is collected during the Bolna confirmation call — the Nova AI agent asks the employee the reason for their visit (Annual Checkup, Blood Test, BP Check, or General OPD). This is passed back to the Spring Boot API and stored with the appointment record. It helps hospitals prepare for the employee's specific needs in advance (e.g., the lab can ready blood test equipment, the doctor can review relevant history).

7 Important Code with Explanation
📌 JWT Authentication Filter
Extracts the Bearer token from every request, validates it, and sets the security context so controllers know who the user is.
JwtAuthFilter.java
protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response,
                                FilterChain filterChain) {
    String authHeader = request.getHeader("Authorization");
    if (authHeader != null && authHeader.startsWith("Bearer ")) {
        Claims claims = jwtUtil.validateToken(authHeader.substring(7));
        var auth = new UsernamePasswordAuthenticationToken(
            new JwtUser(claims.getSubject(), claims.get("name"),
                       claims.get("userId"), claims.get("role")),
            null,
            List.of(new SimpleGrantedAuthority("ROLE_" + claims.get("role")))
        );
        SecurityContextHolder.getContext().setAuthentication(auth);
    }
    filterChain.doFilter(request, response);
}
The JwtUser record carries username, name, userId, and role — available to all controllers via SecurityUtil.getCurrentUser().
📌 Atomic Booking — Double Booking Prevention
Three-layer safety: service check, @Transactional atomicity, and DB unique constraint. This is the most critical business logic in the app.
AppointmentService.java
@Transactional
public Appointment bookAppointment(AppointmentRequest request) {
    Employee employee = employeeService.getEmployeeById(request.getEmployeeId());
    AppointmentSlot slot = slotService.getSlotById(request.getSlotId());

    // Layer 1: Service check
    if (slot.getIsBooked())
        throw new BusinessException("Slot already booked");

    // 1 employee = 1 active booking
    List<Appointment> existing = appointmentRepository.findByEmployeeId(employee.getId());
    if (!existing.isEmpty())
        throw new BusinessException("Employee already has an appointment");

    // Layer 2: Atomic update within @Transactional
    slot.setIsBooked(true);
    slotRepository.save(slot);

    Appointment appointment = new Appointment(employee, slot);
    appointment = appointmentRepository.save(appointment);

    notificationService.notifyAppointmentBooked(appointment);
    return appointment;
}
Without @Transactional, two concurrent requests could both pass the isBooked check before either updates — causing double booking. The annotation ensures read-check-write is atomic.
📌 Data Isolation — Multi-Tenant Security
Every controller call goes through this check. CLIENT users can only access resources where the ID matches their JWT userId. ADMIN bypasses all checks.
SecurityUtil.java
public static JwtUser getCurrentUser() {
    Authentication auth = SecurityContextHolder.getContext().getAuthentication();
    if (auth == null || !auth.isAuthenticated()
        || !(auth.getPrincipal() instanceof JwtUser))
        return null;
    return (JwtUser) auth.getPrincipal();
}

public static void requireOwnership(Long targetId, String role) {
    JwtUser user = getCurrentUser();
    if (user == null) throw new AccessDeniedException("Not authenticated");
    if ("ADMIN".equals(user.role())) return;
    if (!user.role().equals(role) || !user.userId().equals(targetId))
        throw new AccessDeniedException("Access denied");
}
Usage in a controller: SecurityUtil.requireOwnership(clientId, "CLIENT") — blocks any CLIENT user from accessing another client's data. AccessDeniedException maps to 403 Forbidden.

📌 Global Exception Handling
Every exception returns a consistent {status, message, data} JSON. No stack traces leak to the client.
GlobalExceptionHandler.java
@ExceptionHandler(AccessDeniedException.class)
public ResponseEntity<ApiResponse<Void>> handleAccessDenied(AccessDeniedException ex) {
    return ResponseEntity.status(HttpStatus.FORBIDDEN)
        .body(ApiResponse.error("Access denied"));
}

@ExceptionHandler(BusinessException.class)
public ResponseEntity<ApiResponse<Void>> handleBusiness(BusinessException ex) {
    return ResponseEntity.status(HttpStatus.CONFLICT)
        .body(ApiResponse.error(ex.getMessage()));
}

@ExceptionHandler(ResourceNotFoundException.class)
public ResponseEntity<ApiResponse<Void>> handleNotFound(ResourceNotFoundException ex) {
    return ResponseEntity.status(HttpStatus.NOT_FOUND)
        .body(ApiResponse.error(ex.getMessage()));
}

@ExceptionHandler(Exception.class)
public ResponseEntity<ApiResponse<Void>> handleGeneral(Exception ex) {
    return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
        .body(ApiResponse.error("Internal server error: " + ex.getMessage()));
}
HTTP status mapping: 403 → Access denied, 404 → Not found, 409 → Business conflict (e.g. slot booked), 400 → Validation, 500 → Everything else.
📌 API Response Wrapper
Every endpoint returns this wrapper. Frontend always reads response.data.status, response.data.message, response.data.data.
ApiResponse.java
public class ApiResponse<T> {
    private String status;       // "success" | "error"
    private String message;
    private T data;

    public static <T> ApiResponse<T> success(String message, T data) {
        return new ApiResponse<>("success", message, data);
    }

    public static <T> ApiResponse<T> error(String message) {
        return new ApiResponse<>("error", message, null);
    }
}
Consistent API contract: frontend Axios interceptor checks response.data.status === "error" to show toast messages. The data field carries the actual payload (employee list, appointment, etc.).
📌 Security Config — Endpoint Access Rules
Login and public endpoints are permitAll(). Everything else requires a valid JWT. Stateless sessions — no HttpSession.
SecurityConfig.java
@Bean
public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    http
        .cors(c -> c.configurationSource(corsConfig.corsConfigurationSource()))
        .csrf(c -> c.disable())
        .sessionManagement(s -> s.sessionCreationPolicy(STATELESS))
        .authorizeHttpRequests(a -> a
            .requestMatchers("/api/auth/**").permitAll()
            .requestMatchers("/api/employees/verify").permitAll()
            .requestMatchers("/api/admin/verify").permitAll()
            .requestMatchers("/api/chat", "/api/stats", "/").permitAll()
            .anyRequest().authenticated()
        )
        .addFilterBefore(jwtAuthFilter, UsernamePasswordAuthenticationFilter.class);
    return http.build();
}
The JwtAuthFilter runs before Spring's own auth filter. If the JWT is missing or invalid, the request hits .anyRequest().authenticated() and returns 401 Unauthorized.
